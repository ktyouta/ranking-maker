# ランキングへのタグ付与 設計検討

設計検討の記録。バックエンドは作成・更新・削除・復元・詳細取得・タグ一覧取得まで実装済み。フロントエンドは作成・編集でのタグ設定と、閲覧モード・ゴミ箱詳細でのタグ表示まで実装済み。一覧でのタグ表示・タグ検索は未着手（未決事項10）。タグ検索は 2026-09-28 に設計を検討した（決定事項「タグ検索」）。
各項目の出所を以下で区別する。

- **（ユーザー決定）**: ユーザーが発言・指示した内容
- **（Claude提案・未承認）**: Claude が提案し、ユーザーの承認を得ていない内容
- **（Claudeの帰結・未確認）**: ユーザー決定から Claude が導いた結論で、ユーザーに確認していない内容
- **（実装済み）**: ユーザーが実装し、コミット済みのコードから読み取った内容

## 現状（コード調査結果）

- `tag_master`: ユーザー所有のタグ。生存行で `(userId, name)` が一意
- `ranking_tag_master`: ランキングとタグの中間テーブル。`(rankingId, userId)`・`(tagId, userId)` の複合FKで「自分のランキングに自分のタグしか付けられない」をDB制約で担保
- `TagAggregate`: タグそのもの（`TagId`・`UserId`・`TagName`）を表す集約。新規タグの作成時に使う
- `RankingAggregate`: タグ付けを `RankingTagEntity`（`RankingTagId`・`TagId`）の一覧として持つ
- `TagName`: 必須・20文字以内・カンマ（`,`）を含まない（カンマの禁止は 2026-09-28 にタグ検索のため追加）

## 決定事項

### データ構造・ドメイン

- `tag_master` を維持する。タグ名をランキング側に直接持たせる案（案Y）は採用しない（ユーザー決定）
- ランキングに紐づかないタグは存在させない（ユーザー決定）
  - タグ作成用APIでダイアログ内から即時にタグを作る案は不採用（ユーザー決定）
  - 新規タグはランキングの保存時に作成する（ユーザー決定）
- タグの色は選べない。`tag_master` に色のカラムは持たせない（ユーザー決定）

### 画面

- タグの設定はダイアログで行う（ユーザー決定）
  - 理由: タイトルと項目の間にタグ入力欄を置くと、項目までのスクロールが増える（特にスマホ）
- 作成画面・編集モードには、タグと分かるアイコンを置き、タップでダイアログを開く（ユーザー決定）
- 閲覧モードは閲覧のみとし、閲覧モードからタグは変更できない（ユーザー決定）
- 閲覧モードでは、お気に入り・メモ・削除のアイコンと同じ列に、タグ表示ダイアログを開くアイコンを並べる（ユーザー決定）
  - スマホでも4つ並べて収まりそう（ユーザーの実機確認、現状3アイコンの状態で目視）
- タグの見た目は、枠線がテーマカラーで中が白とする。ダークモードは別扱い（ユーザー決定）

### 更新経路

- タグの変更（付け外し・新規作成）は作成画面・編集モードのタグ設定ダイアログでのみ行い、ランキング本体の確定操作と一緒に保存する。更新経路はこの1本のみ（ユーザー決定）
  - タグだけを即時保存する専用経路は設けない
  - 1回の保存処理で、ランキング本体・新規タグ作成・紐づけをまとめて扱う。既存の作成・更新リポジトリと同様に `db.batch` で一括保存する（Claude提案・未承認）

### 使われなくなったタグの削除（未決事項2・3の前半）

- 使われなくなったタグを削除するのは、更新（タグを外したとき）と完全削除の2経路（実装済み）
  - 一括の完全削除は存在しない
- ゴミ箱にあるランキングのタグ付けも「使用中」とみなし、削除の対象にしない（実装済み。`tag-usage.repository.ts` は論理削除された紐づけも数える）
- ゴミ箱への移動・復元では、タグ付けもランキングと一緒に論理削除・復元する（実装済み）

### タグの取得

- ランキング詳細・ゴミ箱詳細の取得APIは、紐づくタグ名をタグ名順で返す（ユーザー決定: ゴミ箱詳細にもタグを表示する）
- タグ一覧取得API（`GET /api/v1/my-ranking/tags`）を設ける（ユーザー決定）
  - ゴミ箱のランキングにしか付いていないタグも候補として返す（ユーザー決定: 未決事項3の後半に対し案Aを選択）
  - 返す項目は `name` のみ、タグ名順（Claude提案・未承認。作成・更新のリクエストがタグ名で送る形のため）

### フロントエンド（2026-09-27 実装）

- 作成画面・編集モードのタグアイコンは「タイトル」ラベル行の右端に置き、件数バッジを重ねる（ユーザー決定: 案P）
- タグ設定ダイアログは作成画面と編集モードの共通部品にする（`components/layouts/tag-select-dialog/`）。状態と処理は各画面の hook が別々に持つ（ユーザー決定）
- タグのチップは共通部品にする（`components/ui/tag-chip/`）。見た目は下記「タグの見た目」の案（ユーザー承認）
- タグ設定ダイアログの中身（ユーザー承認）
  - 上段: 設定中のタグ（「×」で外す。タグがないときは「タグが設定されていません」）
  - 中段: 入力欄と「追加」ボタン（Enter でも追加。日本語変換の確定では追加しない）
  - 下段: これまでに使ったタグの候補（押すと付け外し）
  - 変更はその場でフォームに反映し、確定・取り消しは画面の作成・保存・キャンセルで行う
- 閲覧モード・ゴミ箱詳細のタグ表示ダイアログは、チップを並べ、タグがないときは「タグはありません」と表示する（ユーザー承認）
  - アイコンの並びは、閲覧モードが「お気に入り・メモ・タグ・削除」、ゴミ箱詳細が「メモ・タグ」
- 閲覧モードとゴミ箱詳細の、メモ表示・タグ表示ダイアログは共通部品にする（`components/layouts/memo-view-dialog/`・`components/layouts/tag-view-dialog/`）。メモ表示はランキングのメモと項目のメモの両方に使う（ユーザー決定）
  - 画面ごとに文言・操作が違う確認ダイアログ（削除・復元・完全削除）は各画面に残す
- テンプレートから作成するときは、タグもコピーする（ユーザー決定）
- タグ一覧は、作成・更新・完全削除の後に再取得する（タグが増減する操作のため）

### タグ検索（2026-09-28 設計検討）

#### 対象・範囲

- マイランキング一覧の検索エリアにタグ検索を追加する（ユーザー決定）
- ゴミ箱一覧の検索エリアにも入れる（ユーザー決定）
- 一覧カードへのタグ表示は今回入れない（ユーザー決定）
  - 理由: タグが何個も付くと表示しきれない（ユーザー発言）
  - AND 検索なら、表示されたランキングには選んだタグが必ず全部付いているため、カードに表示しなくてもヒットした理由が分かる（Claudeの帰結・未確認）

#### 画面

- タグは絞り込みパネルからダイアログを開いて選ぶ（ユーザー決定: 案B）
  - 理由: パネルにタグを直接並べる案（案A）は、タグが増えたときに下に伸びすぎる（ユーザー発言）
- 位置は絞り込みパネル内の、お気に入りの行の右横。「タグ」ラベルとダイアログを開くボタンを置く（ユーザー決定）
  - スマホでは各行が「ラベル → 部品」の順で縦に並ぶため、右横でも違和感はない（ユーザー発言）
  - 「お気に入りラベル＋ボタン」と「タグラベル＋ボタン」の2組を横に並べ、スマホでは各組の中でラベルの下に部品を置く（ユーザー承認）

```
PC（sm以上）
お気に入り  [☆ のみ表示]    タグ  [タグを選ぶ]

スマホ
お気に入り        タグ
[☆ のみ表示]      [タグを選ぶ]
```
- 検索用のタグ選択ダイアログは `components/layouts/tag-filter-dialog/` に置き、マイランキングとゴミ箱で共通にする（ユーザー承認）
  - 前例: `memo-view-dialog`・`tag-view-dialog`（閲覧モードとゴミ箱詳細で共通）
  - 既存の `tag-select-dialog` は新規タグの入力欄を持つため、検索には流用しない
  - 選択中のタグの状態は、各画面の hook（`use-my-ranking-list.ts`・`use-trash-list.ts`）が持つ
- 選択中のタグは、絞り込みパネルには並べない。ダイアログを開いたときに選択中と分かればよい（ユーザー決定）
- 絞り込みの件数バッジは、タグを何個選んでも1件と数える（ユーザー承認）
  - 理由: 既存のバッジは項目単位で数えている（登録日は開始日・終了日の両方を入れても1件）

#### 検索条件

- クエリパラメータはタグ名をカンマでつないだ1つの文字列で持つ（例: `tags=A,B`）（ユーザー決定）
  - 当初は同名パラメータを繰り返す形（`tags=A&tags=B`）で実装したが、ユーザーの指示でカンマ区切りに変更した
  - カンマ区切りで区別できるよう、タグ名にカンマ（半角 `,`）を使えないようにする（ユーザー決定）。`TagName.SEPARATOR` を区切り文字の単一の定義とし、`TagName` と作成・更新・一覧取得のスキーマがこれを参照する（実装済み）
  - 全角の「，」「、」は区切り文字ではないため、タグ名に使える（Claudeの帰結・未確認）
  - 作成・編集画面のタグ入力でも、カンマを含むタグを追加できないようにする（Claudeの帰結・未確認。フロントエンドで対応）
  - カンマを含む既存のタグがある場合、そのタグが付いたランキングは、タグを外さないと保存できなくなる（Claudeの帰結・未確認。既存データの有無は未確認）
- 複数のタグを選んだときは AND（すべて付いているもの）で絞り込む（ユーザー決定・暫定。「とりあえずいい」との回答）
  - 他の絞り込み条件もすべて AND で、タグを増やすほど結果が減る方が「絞り込み」として自然
  - 参考: GitHub は `label:"a" label:"b"` で AND、`label:"a","b"` で OR を選べる。Stack Overflow は OR を `[a] or [b]` と明示して書く方式
- 検索条件のタグは最大20個までとする（ユーザー承認）
  - 理由: 1ランキングのタグ上限が20件（`RankingAggregate.MAX_TAG_COUNT`）のため、21個以上選ぶと必ず0件になる

#### SQL（ユーザー承認）

選んだタグごとに `EXISTS` を1つずつ並べる（案1）。既存のキーワード検索（`buildConditions` 内の `exists`）と同じ書き方。

```sql
AND EXISTS (
  SELECT 1 FROM ranking_tag_master rt
  INNER JOIN tag_master t ON t.id = rt.tag_id
  WHERE rt.ranking_id = r.id
    AND rt.delete_flg = false      -- ゴミ箱側は true
    AND t.name = 'ラーメン'
)
AND EXISTS ( ...同じ形で次のタグ )
```

- ゴミ箱側で `rt.delete_flg = true` を使えるのは、紐づけ行の `delete_flg` がランキングのゴミ箱状態と常に一致するため（実装済み）
  - タグを外したときの紐づけ行は物理削除している（`update-my-ranking.repository.ts`）
  - ゴミ箱への移動・復元では、紐づけ行も一緒に論理削除・復元している
  - ゴミ箱一覧の項目の条件も、同じ考え方で `delete_flg = true` にしている

#### 検索候補のタグ一覧

- 候補は「その画面の一覧に出てくるランキングに付いているタグ」だけにする。ゴミ箱にしかないタグをマイランキング側の候補から外す（ユーザー決定・暫定。「とりあえずいい」との回答）
  - 理由: 選ぶと必ず0件になる候補は、検索が壊れているように見える
  - ゴミ箱側も同様に、マイランキングにしか付いていないタグは出さない
- 既存の `GET /api/v1/my-ranking/tags` は、タグ設定ダイアログの候補（ゴミ箱のタグも含む全件）として残す（決定事項「タグの取得」）
- 検索候補用に、次の2本を新しく作る（Claude決定・ユーザー承認）

| 用途 | エンドポイント |
|---|---|
| マイランキング一覧の候補（ゴミ箱に入っていないランキングのタグ） | `GET /api/v1/my-ranking/filter-tags` |
| ゴミ箱一覧の候補（ゴミ箱のランキングのタグ） | `GET /api/v1/my-ranking/trash/filter-tags` |

- 名前の理由: 既存の `tags`（設定の候補）と区別し、「絞り込みの候補」という用途を表すため。末尾を用途名にするのは `export`・`bulk-delete` という前例がある
- ゴミ箱側を `/my-ranking/trash/...` の下に置くのは、一覧の `/my-ranking`・`/my-ranking/trash` の前例に合わせるため
- Controller・Usecase・Repository は2本に分ける（`get-filter-tags.*`・`get-trash-filter-tags.*`）。一覧取得の `get-list-my-ranking`・`get-trash-list-my-ranking` の前例に合わせる
- フロントエンドの呼び出し部分は、それぞれの画面のフォルダに置く（`features/my-ranking/api/get-filter-tags.ts`・`features/trash/api/get-trash-filter-tags.ts`）
  - 既存の `app/api/get-tags.ts` は作成画面と編集画面の両方で使うため `app/api` にある。今回はそれぞれ1画面でしか使わない
- 候補取得のSQL（Claude提案・未承認）

```sql
SELECT t.name FROM tag_master t
WHERE t.user_id = ? AND t.delete_flg = false
  AND EXISTS (
    SELECT 1 FROM ranking_tag_master rt
    WHERE rt.tag_id = t.id
      AND rt.delete_flg = false    -- ゴミ箱側は true
  )
ORDER BY t.name
```

- 実装時の注意（Claudeの帰結・未確認）
  - ルートの登録順: `/my-ranking/filter-tags`・`/my-ranking/trash/filter-tags` は、`:rankingId` 系のルートより前に登録する。後にすると `filter-tags` がランキングIDとして扱われる
  - キャッシュの再取得: 2本とも、作成・更新・ゴミ箱への移動（一括含む）・復元（一括含む）・完全削除のたびに中身が変わる。既存のタグ一覧（作成・更新・完全削除の後だけ再取得）より再取得の契機が多い

#### インデックス

- `tag_master.name` に新しい索引は作らない（ユーザー承認）
  - 理由: 検索は「ランキング → 紐づけ → タグ」の順に辿る。タグは主キーで1行に決まり、名前はその1行を見比べるだけなので、名前の索引は使われない
  - 名前から探す順番で動く場合も、既存の `ux_tag_master_user_name`（`user_id, name`）が使える。複合索引は先頭の列（`user_id`）だけの条件でも使える
- 各部分で使われる見込みの索引（未確認）

| 部分 | マイランキング一覧 | ゴミ箱 |
|---|---|---|
| `rt.ranking_id = r.id` | `ux_ranking_tag_master_ranking_tag` | 使える索引なし（端から読む） |
| `t.id = rt.tag_id` | 主キー | 主キー |
| `t.name = ...` | 使わない | 使わない |

- 既存の2つの索引は `delete_flg = false` の行だけを対象にした部分インデックスである
  - SQLite では、クエリ側に同じ形の条件がないと部分インデックスは使われない（[SQLite – Partial Indexes](https://www.sqlite.org/partialindex.html)）
  - Drizzle が条件をパラメータ（`?`）で渡した場合に使われるかは未確認
  - ゴミ箱側（`delete_flg = true`）では、部分インデックスはそもそも使えない
- 検索候補のSQLは「タグIDから紐づけを探す」ため、`tag_id` から始まる索引がなく、端から読む見込み（未確認）。既存の更新・完全削除の「使われなくなったタグ」の判定も同じ形
- 索引を追加するかは、実装後に Drizzle が生成したSQLで `EXPLAIN QUERY PLAN` を実行して判断する（ユーザー承認）
  - 追加するなら、部分インデックスではない通常の索引（`ranking_tag_master (ranking_id)`・`(tag_id)`）が候補。検索だけでなく、テーブル全体の話として検討する

## Claude提案（未承認）

### ドメインモデル

- 「タグそのもの」と「ランキングへのタグ付け」は別の概念として扱う
  - タグそのもの（`tag_master`）: ランキングとは独立して作成・削除される。`Tag` 単体を集約とする
  - タグ名の重複チェックは、`RankingTitleUniquenessDomainService` と同様にドメインサービスで行う
- 既存の `TagAggregate` は、実質的に「ランキングへのタグ付け」を表している。ただし、他の集約に属するタグ名まで持っているため、別集約はIDで参照する原則に反する
- タグ付けを `RankingAggregate` にタグIDの一覧として持たせるか、タグ付け専用の集約にするかは未決（下記の未決事項1）

### タグの見た目

2026-09-27 にフロント設計とあわせてユーザー承認済み。実装では枠線を `border-2` にしている。

- 枠線を `border-accent`、中を `bg-surface`、文字を `text-ink` にする
  - `bg-surface` はライト3テーマで白、ダークモードで gray-800 に切り替わるため、ダークモード用の個別指定は不要
  - 「テンプレートから作成」ボタン（`border-accent/70 bg-surface text-accent`）と見分けやすくするため、文字色はアクセントカラーにしない

### 作成画面・編集モードのタグアイコン配置

2026-09-27 にユーザーが案Pを選択（決定事項「フロントエンド」を参照）。

- 「タイトル」ラベル行の右端にタグアイコンを置き、付いている件数をバッジで重ねて表示する（案P）
  - タイトル入力欄はラベル行とは別の行なので、タイトルの長さの影響を受けない
  - 幅320pxの端末でも収まる見込み（「タイトル」約72px + アイコン約40px）
  - 作成画面・編集モードの両方に同じラベル行があり、位置を揃えられる
  - 懸念: タイトルの付属物に見える可能性がある

| 置き場所 | 評価 |
|---|---|
| P: 「タイトル」ラベル行の右端 | 推奨 |
| Q: タイトル入力欄の右端 | 入力した文字がアイコンの下に潜るため、右側の余白確保と `Textbox` のアイコン対応が必要 |
| R: ヘッダー行（アイコン選択ボタンの横） | 作成画面のスマホ表示ではすでに折り返しが起きている。編集画面は長いタイトルが折り返すと縦位置がずれる。作成と編集で位置が揃わない |

### 閲覧モードのスマホ確認

- まず4アイコンをそのまま並べ、開発者ツールで幅375px・360pxでも崩れないか確認する
- 更新日チップは `shrink-0` がないため、崩れる場合はチップの文字が2行に折り返す形で現れる
- 崩れた場合の対処候補:
  - アイコン（`p-2`）と更新日チップを少し縮小する。タップ領域は約40pxになる
  - スマホではチップの「更新日」という文字を省く

## 検討して見送った案

- **タイトルと項目の間にチップ入力欄を置く**: 項目までのスクロールが増えるため、ダイアログ方式を採用した
- **閲覧モードでタグを直接編集して即時保存する（お気に入りと同じ扱い）**: 閲覧モードは閲覧のみとしたため不採用
  - 作成画面では使えないため、作成画面だけ別の保存経路が必要になる点もデメリットだった
- **タグ管理画面を別に用意し、フォームでは既存タグから選ぶだけにする**: タグを付けるたびに別画面へ移動する必要があり、ランキング作成の流れが途切れる
- **ダイアログ内で新規タグを即時作成する（タグ作成用APIを別に用意）**: ランキングに紐づかないタグが残るため不採用（ユーザー決定）
- **タグ名をランキング側に直接持たせる（`tag_master` を廃止、案Y）**: ユーザー判断で不採用（ユーザー決定）
- **タグの色を選べるようにする**: 4テーマでの見え方やパレットの管理が必要になるため、色は選べないこととし、枠線をテーマカラーにする方式にした（ユーザー決定）
- **フォームのタグボタンに名前を省略して表示する（例: `🏷 ラーメン・グルメ +1`）**: スマホでは名前がほとんど入らない
- **タグ検索: 絞り込みパネルにタグのチップを直接並べる（案A）**: タグが増えたときに下に伸びすぎる（ユーザー決定）
- **タグ検索: キーワード検索の対象にタグ名を含める（案C）**: 部分一致になり（「ラーメン」で「ラーメン屋」も当たる）、「このタグが付いているもの」という絞り込みにならない。どこに当たったかも区別できない
- **タグ検索: 複数タグを OR で検索する**: タグを増やすほど結果が増え、「絞り込み」と逆の動きになる（AND を暫定採用）
- **タグ検索のSQL: `IN` でまとめて `HAVING COUNT(*) = 選んだ数` とする（案2）**: URLの重複タグや紐づけの一意性といった、SQLの外の前提に正しさが依存する
- **タグ検索の候補に既存のタグ一覧APIをそのまま使う**: 選ぶと必ず0件になるタグが候補に混じる（マイランキング側ではゴミ箱にしかないタグ、ゴミ箱側ではマイランキングにしかないタグ）
- **タグ検索の候補を既存の `/my-ranking/tags` に相乗りさせる（パラメータで切り替える等）**: タグ設定の候補（全件）と絞り込みの候補は中身が違い、用途の違う2つを1つにまとめることになる

## 破綻するケース（現方針）

- 一覧からまとめてタグを付け替える要件が出た場合: タグだけを更新する専用経路が必要になり、タグ付けを `RankingAggregate` から切り出すかどうかを見直すことになる
- 使われなくなったタグの削除処理がどこか1経路でも漏れた場合: 「ランキングに紐づかないタグは存在させない」が崩れる。DB制約では担保できない
- 閲覧モードのアイコンがさらに増えた場合: スマホで1行に収まらなくなる
- 色で見分けたい・分類したいという要望が出た場合: `tag_master` への色カラム追加（色マスタ + 外部キー）と、テーブルを作り直すマイグレーションが必要になる。作り直しの際は `ranking_tag_master` への連鎖削除を防ぐため `PRAGMA foreign_keys=OFF` が必要
- 公開ランキング等でタグを他のユーザーと共有する要件が出た場合: タグがユーザー所有である前提から見直しが必要になる
- 「ラーメン」「らーめん」のような似たタグを使い分けるユーザーが多い場合: タグ検索は OR の方が欲しくなり、AND/OR の切り替えが必要になる
- 絞り込みの候補にタグ以外（アイコンの種類等）も加える場合: 候補ごとにAPIを増やすのではなく、絞り込みの候補をまとめて返すAPIに作り直すかを検討することになる
- ゴミ箱のランキングが大量になった場合: ゴミ箱側のタグ検索は使える索引がなく、端から読むため遅くなる可能性がある
