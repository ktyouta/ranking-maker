# ランキングへのタグ付与 設計検討

設計検討の記録。バックエンドは作成・更新・削除・復元・詳細取得・タグ一覧取得まで実装済み。フロントエンドは作成・編集でのタグ設定と、閲覧モード・ゴミ箱詳細でのタグ表示まで実装済み。一覧でのタグ表示・タグ検索は未着手（未決事項10）。
各項目の出所を以下で区別する。

- **（ユーザー決定）**: ユーザーが発言・指示した内容
- **（Claude提案・未承認）**: Claude が提案し、ユーザーの承認を得ていない内容
- **（Claudeの帰結・未確認）**: ユーザー決定から Claude が導いた結論で、ユーザーに確認していない内容
- **（実装済み）**: ユーザーが実装し、コミット済みのコードから読み取った内容

## 現状（コード調査結果）

- `tag_master`: ユーザー所有のタグ。生存行で `(userId, name)` が一意
- `ranking_tag_master`: ランキングとタグの中間テーブル。`(rankingId, userId)`・`(tagId, userId)` の複合FKで「自分のランキングに自分のタグしか付けられない」をDB制約で担保
- `TagAggregate`: タグそのもの（`TagId`・`UserId`・`TagName`）を表す集約。新規タグの作成時に使う
- `RankingAggregate`: タグ付けを `RankingTagEntity`（`RankingTagId`・`TagId`）の一覧として持つ
- `TagName`: 必須・20文字以内

## 決定事項

### データ構造・ドメイン

- `tag_master` を維持する。タグ名をランキング側に直接持たせる案（案Y）は採用しない（ユーザー決定）
- ランキングに紐づかないタグは存在させない（ユーザー決定）
  - タグ作成用APIでダイアログ内から即時にタグを作る案は不採用（ユーザー決定）
  - 新規タグはランキングの保存時に作成する（ユーザー決定）
- タグの色は選べない。`tag_master` に色のカラムは持たせない（ユーザー決定）

### 画面

- タグの設定はダイアログで行う（ユーザー決定）
  - 理由: タイトルと項目の間にタグ入力欄を置くと、項目までのスクロールが増える（特にスマホ）
- 作成画面・編集モードには、タグと分かるアイコンを置き、タップでダイアログを開く（ユーザー決定）
- 閲覧モードは閲覧のみとし、閲覧モードからタグは変更できない（ユーザー決定）
- 閲覧モードでは、お気に入り・メモ・削除のアイコンと同じ列に、タグ表示ダイアログを開くアイコンを並べる（ユーザー決定）
  - スマホでも4つ並べて収まりそう（ユーザーの実機確認、現状3アイコンの状態で目視）
- タグの見た目は、枠線がテーマカラーで中が白とする。ダークモードは別扱い（ユーザー決定）

### 更新経路

- タグの変更（付け外し・新規作成）は作成画面・編集モードのタグ設定ダイアログでのみ行い、ランキング本体の確定操作と一緒に保存する。更新経路はこの1本のみ（ユーザー決定）
  - タグだけを即時保存する専用経路は設けない
  - 1回の保存処理で、ランキング本体・新規タグ作成・紐づけをまとめて扱う。既存の作成・更新リポジトリと同様に `db.batch` で一括保存する（Claude提案・未承認）

### 使われなくなったタグの削除（未決事項2・3の前半）

- 使われなくなったタグを削除するのは、更新（タグを外したとき）と完全削除の2経路（実装済み）
  - 一括の完全削除は存在しない
- ゴミ箱にあるランキングのタグ付けも「使用中」とみなし、削除の対象にしない（実装済み。`tag-usage.repository.ts` は論理削除された紐づけも数える）
- ゴミ箱への移動・復元では、タグ付けもランキングと一緒に論理削除・復元する（実装済み）

### タグの取得

- ランキング詳細・ゴミ箱詳細の取得APIは、紐づくタグ名をタグ名順で返す（ユーザー決定: ゴミ箱詳細にもタグを表示する）
- タグ一覧取得API（`GET /api/v1/my-ranking/tags`）を設ける（ユーザー決定）
  - ゴミ箱のランキングにしか付いていないタグも候補として返す（ユーザー決定: 未決事項3の後半に対し案Aを選択）
  - 返す項目は `name` のみ、タグ名順（Claude提案・未承認。作成・更新のリクエストがタグ名で送る形のため）

### フロントエンド（2026-09-27 実装）

- 作成画面・編集モードのタグアイコンは「タイトル」ラベル行の右端に置き、件数バッジを重ねる（ユーザー決定: 案P）
- タグ設定ダイアログは作成画面と編集モードの共通部品にする（`components/layouts/tag-select-dialog/`）。状態と処理は各画面の hook が別々に持つ（ユーザー決定）
- タグのチップは共通部品にする（`components/ui/tag-chip/`）。見た目は下記「タグの見た目」の案（ユーザー承認）
- タグ設定ダイアログの中身（ユーザー承認）
  - 上段: 設定中のタグ（「×」で外す。タグがないときは「タグが設定されていません」）
  - 中段: 入力欄と「追加」ボタン（Enter でも追加。日本語変換の確定では追加しない）
  - 下段: これまでに使ったタグの候補（押すと付け外し）
  - 変更はその場でフォームに反映し、確定・取り消しは画面の作成・保存・キャンセルで行う
- 閲覧モード・ゴミ箱詳細のタグ表示ダイアログは、チップを並べ、タグがないときは「タグはありません」と表示する（ユーザー承認）
  - アイコンの並びは、閲覧モードが「お気に入り・メモ・タグ・削除」、ゴミ箱詳細が「メモ・タグ」
- 閲覧モードとゴミ箱詳細の、メモ表示・タグ表示ダイアログは共通部品にする（`components/layouts/memo-view-dialog/`・`components/layouts/tag-view-dialog/`）。メモ表示はランキングのメモと項目のメモの両方に使う（ユーザー決定）
  - 画面ごとに文言・操作が違う確認ダイアログ（削除・復元・完全削除）は各画面に残す
- テンプレートから作成するときは、タグもコピーする（ユーザー決定）
- タグ一覧は、作成・更新・完全削除の後に再取得する（タグが増減する操作のため）

## Claude提案（未承認）

### ドメインモデル

- 「タグそのもの」と「ランキングへのタグ付け」は別の概念として扱う
  - タグそのもの（`tag_master`）: ランキングとは独立して作成・削除される。`Tag` 単体を集約とする
  - タグ名の重複チェックは、`RankingTitleUniquenessDomainService` と同様にドメインサービスで行う
- 既存の `TagAggregate` は、実質的に「ランキングへのタグ付け」を表している。ただし、他の集約に属するタグ名まで持っているため、別集約はIDで参照する原則に反する
- タグ付けを `RankingAggregate` にタグIDの一覧として持たせるか、タグ付け専用の集約にするかは未決（下記の未決事項1）

### タグの見た目

2026-09-27 にフロント設計とあわせてユーザー承認済み。実装では枠線を `border-2` にしている。

- 枠線を `border-accent`、中を `bg-surface`、文字を `text-ink` にする
  - `bg-surface` はライト3テーマで白、ダークモードで gray-800 に切り替わるため、ダークモード用の個別指定は不要
  - 「テンプレートから作成」ボタン（`border-accent/70 bg-surface text-accent`）と見分けやすくするため、文字色はアクセントカラーにしない

### 作成画面・編集モードのタグアイコン配置

2026-09-27 にユーザーが案Pを選択（決定事項「フロントエンド」を参照）。

- 「タイトル」ラベル行の右端にタグアイコンを置き、付いている件数をバッジで重ねて表示する（案P）
  - タイトル入力欄はラベル行とは別の行なので、タイトルの長さの影響を受けない
  - 幅320pxの端末でも収まる見込み（「タイトル」約72px + アイコン約40px）
  - 作成画面・編集モードの両方に同じラベル行があり、位置を揃えられる
  - 懸念: タイトルの付属物に見える可能性がある

| 置き場所 | 評価 |
|---|---|
| P: 「タイトル」ラベル行の右端 | 推奨 |
| Q: タイトル入力欄の右端 | 入力した文字がアイコンの下に潜るため、右側の余白確保と `Textbox` のアイコン対応が必要 |
| R: ヘッダー行（アイコン選択ボタンの横） | 作成画面のスマホ表示ではすでに折り返しが起きている。編集画面は長いタイトルが折り返すと縦位置がずれる。作成と編集で位置が揃わない |

### 閲覧モードのスマホ確認

- まず4アイコンをそのまま並べ、開発者ツールで幅375px・360pxでも崩れないか確認する
- 更新日チップは `shrink-0` がないため、崩れる場合はチップの文字が2行に折り返す形で現れる
- 崩れた場合の対処候補:
  - アイコン（`p-2`）と更新日チップを少し縮小する。タップ領域は約40pxになる
  - スマホではチップの「更新日」という文字を省く

## 検討して見送った案

- **タイトルと項目の間にチップ入力欄を置く**: 項目までのスクロールが増えるため、ダイアログ方式を採用した
- **閲覧モードでタグを直接編集して即時保存する（お気に入りと同じ扱い）**: 閲覧モードは閲覧のみとしたため不採用
  - 作成画面では使えないため、作成画面だけ別の保存経路が必要になる点もデメリットだった
- **タグ管理画面を別に用意し、フォームでは既存タグから選ぶだけにする**: タグを付けるたびに別画面へ移動する必要があり、ランキング作成の流れが途切れる
- **ダイアログ内で新規タグを即時作成する（タグ作成用APIを別に用意）**: ランキングに紐づかないタグが残るため不採用（ユーザー決定）
- **タグ名をランキング側に直接持たせる（`tag_master` を廃止、案Y）**: ユーザー判断で不採用（ユーザー決定）
- **タグの色を選べるようにする**: 4テーマでの見え方やパレットの管理が必要になるため、色は選べないこととし、枠線をテーマカラーにする方式にした（ユーザー決定）
- **フォームのタグボタンに名前を省略して表示する（例: `🏷 ラーメン・グルメ +1`）**: スマホでは名前がほとんど入らない

## 破綻するケース（現方針）

- 一覧からまとめてタグを付け替える要件が出た場合: タグだけを更新する専用経路が必要になり、タグ付けを `RankingAggregate` から切り出すかどうかを見直すことになる
- 使われなくなったタグの削除処理がどこか1経路でも漏れた場合: 「ランキングに紐づかないタグは存在させない」が崩れる。DB制約では担保できない
- 閲覧モードのアイコンがさらに増えた場合: スマホで1行に収まらなくなる
- 色で見分けたい・分類したいという要望が出た場合: `tag_master` への色カラム追加（色マスタ + 外部キー）と、テーブルを作り直すマイグレーションが必要になる。作り直しの際は `ranking_tag_master` への連鎖削除を防ぐため `PRAGMA foreign_keys=OFF` が必要
- 公開ランキング等でタグを他のユーザーと共有する要件が出た場合: タグがユーザー所有である前提から見直しが必要になる
