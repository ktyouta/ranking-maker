## ケース3: 値の履歴確認で根本原因が変わる（z-index 衝突）

### 状況
- ヘッダーのユーザーメニューパネルを展開すると、背面のカードの☆ボタン（`absolute z-20`）がパネルを貫通して前面に見える

### Step 1 出力

```
## 原因調査結果

### 再現条件
- ヘッダーのユーザーメニューを開いた状態で、背面にランキングカード（お気に入り☆ボタン付き）が表示されている

### 原因箇所
- ファイル: frontend/src/features/my-ranking/components/ranking-card.tsx:33
- ファイル: frontend/src/components/layouts/dashboard/dashboard.tsx:122
- 原因: ☆ボタンとユーザーメニューパネルがどちらも z-20 で、祖先にスタッキングコンテキストの境界がないため同一階層で並置され、DOM 出現順（カードが後）で☆ボタンが勝つ

### 値の履歴確認
- 導入コミット: カード内コンテンツ div の `z-10` は 88374d4（2026-09-06）で追加。この時点でカード内に absolute 配置の兄弟要素は存在せず、機能的な必要性はなかった
- ☆ボタンの `z-20` は 9c03c43（2026-09-13）で追加。「コンテンツ div の z-10 より前面に出す」ためだけに選ばれており、ページ全体（ヘッダー）の z-index は考慮されていなかった
- 導入時点での必要性: なかった（コンテンツ div 側の z-10 は当時不要な値であり、それに引きずられて☆ボタン側の z-20 も選ばれた）

### 根本原因
- 機能的必要性のないまま付与されていたカード側の z-index が、後続の機能追加で連鎖的に z-index の値を押し上げ、結果としてページ全体（ヘッダー）のスタッキング順と衝突した
```

### 修正後の対応
- カードルートに `isolate` を追加し、カード内部の z-index がページ全体に漏れないよう境界を作る
- 導入時点で不要だったカード側の `relative z-10` は削除する（refactor スキルで実施、振る舞いが変わらないことをテストで確認）
